# `(srfi s224 fxmappings)` — SRFI-224

```scheme
(import (srfi s224 fxmappings))   ; or (srfi 224), or (srfi srfi-224)
```

[SRFI-224](https://srfi.schemers.org/srfi-224/) Integer Mappings: immutable, finite maps from exact-integer keys ("fxmappings") to arbitrary values — the same shape of API SRFI-146's general mappings have, specialized for integer keys.

```scheme
(define m (fxmapping 1 'a 2 'b 3 'c))
(fxmapping-ref m 2 (lambda () 'not-found))   ; => b
(fxmapping-keys m)                           ; => (1 2 3)
```

## Representation note

Curry's numeric tower promotes fixnums to bignums transparently with no user-visible distinction, and exposes no `fixnum?` predicate — this library accepts **any exact integer** as a key, strictly more permissive than the spec's own machine-word-range restriction, never less.

This implementation backs every fxmapping with a sorted (ascending by key), immutable association list, **not** the SRFI's own sample implementation's big-endian Patricia (radix) tree. Every ordering and traversal guarantee the spec makes is honored exactly; the asymptotic cost is O(n) per operation rather than the reference's O(min(n, W)). This is a deliberate tradeoff matching this codebase's established practice of shipping a correct, straightforward implementation first — see e.g. [`(srfi 132)`](s132-s133.md)'s sorting procedures, which are "just" a stable merge sort even where the spec permits something asymptotically fancier — rather than deferring a whole SRFI on a from-scratch tree data structure.

## The workhorse: `fxmapping-alter`

```scheme
(fxmapping-alter fxmap k failure success)
```

Mirrors [`(srfi 225)`](s225.md)'s own `dict-find-update!` design exactly. If `k` is absent, calls `(failure insert ignore)` — `(insert v)` adds `k`→`v` and returns the new mapping, `(ignore)` returns `fxmap` unchanged. If `k` is present, calls `(success k v replace delete)` — `(replace new-v)` replaces the value, `(delete)` removes the association. Every other single-key updater (`fxmapping-adjoin`, `fxmapping-set`, `fxmapping-delete`, `fxmapping-adjust`) is one `fxmapping-alter` call choosing which continuation to invoke.

`fxmapping-update` is a related but distinct, simpler primitive: `(fxmapping-update fxmap k proc [failure])` requires `k` to already exist (`proc` is called as `(proc k v replace delete)`, same replace/delete shape); on a missing key, the given `failure` **thunk**'s return value is returned directly as `fxmapping-update`'s own result — unlike `fxmapping-alter`'s `failure`, it is *not* itself routed through `insert`/`ignore`, since it need not return a mapping at all.

## Constructors

`(fxmapping k obj ...)` — alternating key/value arguments; earlier associations win on a duplicate key. `(fxmapping-unfold stop? mapper successor seed ...)` — ordinary recursive unfold (unlike [`(srfi 189)`](s189.md)'s unusually restrictive `maybe-unfold`): loops until `stop?`, `mapper` returns `(values key value)` per step, `successor` computes the next seeds. `(fxmapping-accumulate proc seed ...)` — `proc` receives an `abort` continuation plus the seeds and returns `(values key value new-seed ...)`; calling `abort` at any point returns whatever's been accumulated so far, immediately. `(alist->fxmapping alist)` / `(alist->fxmapping/combinator proc alist)` — first occurrence wins by default; `proc` combines `(k old new)` for a duplicate key within the input.

## Everything else

Predicates (`fxmapping-contains?`, `-empty?`, `-disjoint?`), accessors (`fxmapping-ref[/default]`, `fxmapping-min`/`-max`), the rest of the updaters (`-adjoin[/combinator]`, `-set`, `-adjust`, `-delete[-all]`, `-delete-min/-max`, `-update-min/-max`, `-pop-min/-max`), whole-mapping queries (`-size`, `-find`, `-count`, `-any?`, `-every?`), traversal (`-map`, `-for-each`, `-fold[-right]`, `-map->list`, `-relation-map`), filtering (`-filter`, `-remove`, `-partition`), conversion (`->alist`, `->decreasing-alist`, `-keys`, `-values`, `->generator`, `->decreasing-generator`), comparison (`=?`/`<?`/`<=?`/`>?`/`>=?`, all taking a [SRFI-128](s128.md) comparator for *value* equality — keys always compare with `=`), set-theoretic combination (`-union`, `-intersection`, `-difference`, `-xor`, and `/combinator` variants of the first two), and sorted-key interval queries (`-open-interval`, `-closed-interval`, `-open-closed-interval`, `-closed-open-interval`, `fxsubmapping=`/`<`/`<=`/`>`/`>=`, `-split`) all follow the spec's own signatures directly — see the [SRFI-224 text](https://srfi.schemers.org/srfi-224/) for exact per-procedure semantics.

`fxmapping-map`'s dynamic application order is explicitly unspecified by the SRFI's own text — unlike `(srfi 225)`'s `dict-for-each` (which needed a strictly-sequential workaround for exactly this reason), plain `map` (which curry auto-parallelizes above 8 elements) is safe and spec-conformant to use directly here, with no ordering workaround needed. `fxmapping-relation-map`'s behavior for a non-injective transform is explicitly "unpredictable" per the spec; this implementation resolves a key collision by keeping whichever mapped pair is processed last, one reasonable, non-crashing choice among several the spec itself declines to pin down.
