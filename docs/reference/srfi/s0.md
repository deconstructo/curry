# SRFI-0 — `cond-expand`

No import needed — unlike every other library on the [availability table](index.md), SRFI-0 is not a `(srfi sN name)` shim. `cond-expand` is one of curry's ~40 hardcoded special forms (`S_COND_EXPAND`), dispatched directly by the compiler/evaluator, backed by the `(features)` builtin — always active, no `(import ...)` required. Same situation as [SRFI-61](s61.md), from the other direction: a construct that predates the library system entirely and is baked directly into the language core.

[SRFI-0](https://srfi.schemers.org/srfi-0/): feature-based conditional expansion — pick the first clause whose feature requirement is satisfied, at expansion time, or signal an error if none match. SRFI-0 defines exactly one construct (no procedures) with four requirement shapes: a bare `<identifier>`, `(and req ...)`, `(or req ...)`, `(not req)`, plus `else`. Curry's own `cond-expand` is a strict superset — it also accepts R7RS's later `(library (name ...))` requirement (checking whether that library name would successfully import right now), which SRFI-0's own text explicitly anticipates ("future module system SRFIs will need to extend the semantics of SRFI 0").

```scheme
(cond-expand
  (curry 'running-on-curry)
  (else 'somewhere-else))

(cond-expand
  ((and curry (library (curry sync))) 'has-real-threads)
  (else 'no-threads))
```

#### `(features)` → *list of symbols*

Every feature identifier curry currently reports as satisfied — includes `r7rs`, `curry`, platform identifiers (`darwin`/`linux`/etc.), and more. `cond-expand`'s bare-identifier clauses test membership in exactly this list.

`cond-expand` is valid both as an ordinary top-level/body expression and as a `define-library` declaration (its matched clause's body is spliced in as further declarations, not evaluated as expressions) — see `tests/cond_expand_tests.scm` for both positions exercised, including nested `cond-expand` inside a `define-library`.
