# `(srfi s158 generators-and-accumulators)` — SRFI-158

```scheme
(import (srfi s158 generators-and-accumulators))
```

[SRFI-158](https://srfi.schemers.org/srfi-158/): a *generator* is a thunk (zero-argument procedure) that returns successive values on each call, and the eof-object once exhausted. Every combinator below builds directly on that representation — a generator you write by hand (any thunk with that contract) works with all of them, no special construction needed.

## Making generators

#### `(generator v ...)` → *generator*

Yields `v ...` in order, then exhausts.

#### `(list->generator lst)` → *generator*
#### `(vector->generator v [start [end]])` → *generator*
#### `(string->generator s [start [end]])` → *generator*

#### `(make-range-generator start)` → *generator* — infinite, `start`, `start+1`, ...
#### `(make-range-generator start end)` → *generator* — `[start, end)`
#### `(make-range-generator start end step)` → *generator*

#### `(make-iota-generator count)` → *generator*
#### `(make-iota-generator count start)` → *generator*
#### `(make-iota-generator count start step)` → *generator*

Like `(srfi s1 lists)`'s `iota`, but as a generator: exactly `count` values.

#### `(circular-generator v ...)` → *generator*

Yields `v ...` forever, wrapping around. `(circular-generator)` (zero values) exhausts immediately rather than looping.

#### `(make-coroutine-generator proc)` → *generator*

`proc` is called as `(proc yield)`; each call to `yield` (a procedure `proc` receives) suspends `proc` and produces one value from the generator, resuming `proc` the next time the generator thunk is called. **Implemented on a real OS thread** (curry's actor `spawn`, handed off through a `(curry sync)` mutex/condvar rendezvous) rather than a genuine first-class continuation — curry's escape-only continuations (`setjmp`/`longjmp`, no CPS) can't suspend/resume a paused computation the way this needs. Functionally transparent from the generator's own interface, but worth knowing if you're reasoning about performance (a real thread per active coroutine generator) or about what happens if `proc` raises (the thread reports it as simply exhausted — the exception is not propagated to the generator's caller).

```scheme
(define g (make-coroutine-generator
           (lambda (yield) (yield 1) (yield 2) (yield 3))))
(list (g) (g) (g) (eof-object? (g)))  ; => (1 2 3 #t)
```

#### `(make-for-each-generator for-each-proc collection)` → *generator*

Turns any `for-each`-shaped iteration (`(for-each-proc proc collection)`, calling `proc` once per element) into a generator, via `make-coroutine-generator`.

## Consuming generators

#### `(generator->list gen)` → *list*
#### `(generator->list gen n)` → *list, at most `n` elements*
#### `(generator->vector gen [n])` → *vector*
#### `(generator->string gen [n])` → *string*
#### `(generator-length gen)` → *exact integer* — exhausts `gen` counting elements

```scheme
(generator->list (gtake (make-range-generator 0) 5))  ; => (0 1 2 3 4)
```

## Generator combinators (each returns a new generator, doesn't consume its input eagerly)

#### `(gtake gen n)` → *generator, capped at `n` elements*
#### `(gdrop gen n)` → *`gen` itself, after eagerly discarding its next `n` elements*

Unlike every other combinator here, `gdrop` isn't lazy — it immediately calls `gen` `n` times (for effect) and returns `gen`, not a wrapper.

#### `(gappend gen ...)` → *generator* — concatenates, in order
#### `(gcons* v ... gen)` → *generator* — prepends fixed values `v ...` before `gen`'s own output

```scheme
(generator->list (gcons* 'a 'b (list->generator '(1 2))))  ; => (a b 1 2)
```

#### `(gmap proc gen ...)` → *generator*

Applies `proc` to one value from each `gen` per step, like `map` but pulling lazily; exhausts as soon as *any* input generator does.

#### `(gzip gen ...)` → *generator of lists*

`(gmap list gen ...)`.

```scheme
(generator->list (gzip (list->generator '(1 2 3)) (list->generator '(a b c))))
; => ((1 a) (2 b) (3 c))
```

#### `(gfilter pred gen)` → *generator* — only values where `pred` is true
#### `(gremove pred gen)` → *generator* — only values where `pred` is `#f`

#### `(gflatten gen-of-lists)` → *generator*

`gen-of-lists` yields lists; `gflatten` yields their elements one at a time, splicing each list in as it's consumed.

## Folding generators

#### `(generator-map->list proc gen)` → *list* — exhausts `gen`
#### `(generator-fold proc knil gen)` → *value*

`(proc value acc)` for each element, threading the accumulator from `knil` — note the argument order, `proc` gets the *new value first*, accumulator second (opposite of SRFI-1's `fold`, which this SRFI's own text specifies this way).

#### `(generator-for-each proc gen)`
#### `(generator-each proc gen)` — alias for `generator-for-each`
#### `(generator-count pred gen)` → *exact integer*
#### `(generator-any pred gen)` → *`pred`'s result on the first match, or `#f`*
#### `(generator-every pred gen)` → *`pred`'s result on the last element, or `#t` if `gen` was empty*
#### `(generator-find pred gen)` → *the first matching value, or `#f`*

All of these consume `gen` up to the point they stop (which may be short of exhausting it, for `-any`/`-find`).

## Accumulators

An accumulator is a procedure of one argument: call it with a value to fold that value in (and get the accumulated-so-far result back); call it with `(eof-object)` to get the finalized result *without* adding anything.

#### `(make-accumulator kons knil)` → *accumulator*
#### `(make-accumulator kons knil finalizer)` → *accumulator*

`kons` is called as `(kons value acc)` each time the accumulator is called with a real value; `finalizer` (default: identity) is applied to the current state both on every call *and* specifically when finalizing with the eof-object.

```scheme
(define acc (list-accumulator))
(acc 1) (acc 2) (acc 3)
(acc (eof-object))  ; => (1 2 3)
```

#### `(count-accumulator)` → *accumulator, counts calls*
#### `(list-accumulator)` → *accumulator, collects into a list, insertion order*
#### `(reverse-list-accumulator)` → *accumulator, collects into a list, most-recent-first*
#### `(vector-accumulator)` → *accumulator, collects into a vector, insertion order*
#### `(sum-accumulator)` → *accumulator, running sum, starts at 0*
#### `(product-accumulator)` → *accumulator, running product, starts at 1*
