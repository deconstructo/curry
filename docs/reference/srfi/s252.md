# `(srfi s252 property-testing)` — SRFI-252

```scheme
(import (srfi s252 property-testing))
```

[SRFI-252](https://srfi.schemers.org/srfi-252/): property-based testing on top of [`(srfi s64 testing)`](s64.md) — instead of one hand-written assertion, a *property* (a predicate) is checked against many pseudorandom inputs drawn from [`(srfi s158 generators-and-accumulators)`](s158.md)-shaped generators. Test-runner integration is built entirely on s64's exported public API (`%run-assert`, `test-skip`, `test-expect-fail`) rather than any private internals, so pass/fail/xpass/xfail/skip bookkeeping is exactly s64's own, verified logic.

## Testing forms

Each form needs an active test runner — use inside `(test-begin ...) ... (test-end)`, same as any other s64 test case.

#### `(test-property property generator-list)`
#### `(test-property property generator-list runs)`

Draws one input from each generator in `generator-list` (in order — the first generator supplies `property`'s first argument, and so on), calls `(apply property inputs)`, and repeats `runs` times (default 100). Passes if `property` was true every time; fails on the first `#f` result or the first raised exception.

```scheme
(test-begin "square-root")
(test-property (lambda (x) (= (sqrt (* x x)) (abs x))) (list (real-generator)) 50)
(test-end "square-root")
```

#### `(test-property-expect-fail property generator-list)`
#### `(test-property-expect-fail property generator-list runs)`

Same trial run as `test-property`, but the outcome is inverted for reporting: a property that actually fails is recorded `xfail` (expected failure, not counted against the suite), one that unexpectedly holds for every input is recorded `xpass`.

#### `(test-property-skip property generator-list)`
#### `(test-property-skip property generator-list runs)`

Registers the case as skipped without ever calling `property` or drawing any inputs.

#### `(test-property-error property generator-list)`
#### `(test-property-error property generator-list runs)`

Expects `property` to raise *some* exception on every run. Passes if every run raised; fails on the first run that returns normally.

```scheme
(define (parse-then-fail str) (car str))  ; wrong on purpose: str is a string, not a pair
(test-property-error parse-then-fail (list (string-generator)))
```

#### `(test-property-error-type error-type property generator-list)`
#### `(test-property-error-type error-type property generator-list runs)`

Like `test-property-error`, but the exception must also match `error-type` — either `#t` (matches anything, same as `test-property-error`) or a one-argument predicate applied to the raised condition. Curry has no SRFI-36 condition-type hierarchy, so pass a predicate (`error-object?`, or your own guard) rather than a symbolic condition-type name — this is the same convention `(srfi s64 testing)`'s own `test-error` already uses.

```scheme
(test-property-error-type error-object?
  (lambda (n) (error "always fails" n))
  (list (integer-generator)))
```

## `(property-test-runner)`

A `test-runner` (usable with `test-with-runner`, or installed automatically the same way `test-runner-simple` is) that adds property-testing-aware output on failure: which inputs triggered it, and the underlying error if the property raised.

```scheme
(test-with-runner (property-test-runner)
  (test-begin "example")
  (test-property (lambda (x) (> x -1000000)) (list (integer-generator)) 500)
  (test-end "example"))
```

## Generators

Every generator below is an infinite thunk — the [`(srfi s158)`](s158.md) protocol without the exhaustion case. Any hand-written or s158-derived thunk with the same shape works as a `test-property` generator too, as long as it doesn't exhaust within `runs` calls; if a generator does return the eof-object, `test-property` (and the other testing forms) raise a clear error rather than silently passing it through as an input value.

Each generator's first call or two return the "interesting values" the SRFI specifies (`0`, `1`, `-1`, boundary flonums, `+inf.0`/`+nan.0`, and so on); every call after that draws uniformly at random. Numeric ranges, string/list/vector/bytevector lengths, and the random character codepoint range are all implementation-defined, per the SRFI — curry keeps them small and finite (see the source for exact bounds) rather than sampling the full theoretical range, so property tests run fast by default.

#### `(boolean-generator)` → `#t`, `#f`, then uniform
#### `(char-generator)` → `#\null`, then any Unicode scalar value (excluding surrogates)
#### `(string-generator)` → `""`, then random strings
#### `(symbol-generator)` → the empty symbol, then random symbols
#### `(bytevector-generator)` → `#u8()`, then random bytevectors

### Numbers

#### `(integer-generator)`, `(real-generator)`, `(rational-generator)`, `(number-generator)`

Each uniformly samples between its exact and inexact counterpart below on every call.

#### `(complex-generator)`

Curry's complex numbers are always inexact internally — `(exact? (make-rectangular 1/2 1/3))` is `#f` — so per the SRFI's own allowance for that situation, this aliases `inexact-complex-generator` outright rather than sampling between an exact and inexact form.

#### `(exact-integer-generator)` → `0 1 -1`, then random exact integers
#### `(exact-rational-generator)`, `(exact-real-generator)` → `0 1 -1 1/2 -1/2`, then random exact rationals (curry has no exact irrational reals, so these two are identical)
#### `(exact-number-generator)` → uniformly samples the two generators above

#### `(exact-complex-generator)`, `(exact-integer-complex-generator)`

Both **raise an error** unconditionally — curry has no exact complex representation to generate, and the SRFI explicitly permits erroring here rather than requiring a fallback.

#### `(inexact-integer-generator)` → `0.0 -0.0 1.0 -1.0`, then random inexact integers
#### `(inexact-rational-generator)` → `0.0 -0.0 0.5 -0.5 1.0 -1.0`, then random inexact rationals
#### `(inexact-real-generator)` → the above plus `+inf.0 -inf.0 +nan.0`, then any random flonum
#### `(inexact-complex-generator)` → a handful of special-value combinations (`0.0+0.0i`, infinities/NaN on either component), then random complex flonums
#### `(inexact-number-generator)` → uniformly samples `inexact-integer-generator` and `inexact-complex-generator`

## Composite generators

#### `(list-generator-of subgenerator)`
#### `(list-generator-of subgenerator max-length)`

`'()`, then random-length lists (`1` to `max-length` elements, default implementation-defined) of values from `subgenerator`.

```scheme
((list-generator-of (integer-generator)))              ; => ()
((list-generator-of (integer-generator)))              ; => (3 -1 47 0 ...)
```

#### `(vector-generator-of subgenerator)`
#### `(vector-generator-of subgenerator max-length)`

Same as `list-generator-of`, producing vectors.

#### `(pair-generator-of subgenerator-car)`
#### `(pair-generator-of subgenerator-car subgenerator-cdr)`

`(cons (subgenerator-car) (subgenerator-cdr))` each call — if `subgenerator-cdr` is omitted, `subgenerator-car` populates both.

#### `(procedure-generator-of subgenerator)`

Each call produces a *new* variadic procedure that ignores whatever arguments it's later called with and always returns one value sampled from `subgenerator` at the moment the procedure was generated:

```scheme
(define proc-gen (procedure-generator-of (boolean-generator)))
((proc-gen) 1)            ; => #t or #f
((proc-gen) 'foo 'bar)    ; => #t or #f (independently sampled)
```

## No `current-random-source`

Unlike the SRFI's own sample implementation, there's no swappable random-source parameter here — curry's `random-integer`/`random-real` draw from a single global stream (the same one [`(srfi s27 random-bits)`](s27.md)'s `default-random-source` names), with no per-call source override. Runs aren't reproducible by seeding a source object; the closest equivalent is calling `random-source-pseudo-randomize!` on the global stream before the test suite runs.
