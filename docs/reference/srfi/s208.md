# `(srfi s208 nan-procedures)` — SRFI-208

```scheme
(import (srfi s208 nan-procedures))   ; or (srfi 208), or (srfi srfi-208)
```

[SRFI-208](https://srfi.schemers.org/srfi-208/) NaN procedures: dissect and construct IEEE-754 binary64 NaN values by their sign/quiet/payload bit fields. Ordinary Scheme arithmetic on a NaN never exposes these bits (an operation is free to canonicalize or collapse them) — the only way to actually inspect or construct a specific NaN encoding is to bit-pun the underlying double's raw 64-bit representation, exactly the technique the SRFI's own reference implementation uses (a C union).

Curry has no such union exposed to Scheme, so this library is layered on two small new core primitives added alongside it: `%flonum-raw-bits`/`%raw-bits->flonum` (`src/builtins.c`), a `memcpy`-based double↔uint64 bit-pun and nothing more. Every field extraction/construction below is ordinary Scheme bitwise-integer arithmetic against that raw pattern.

## Bit layout

The SRFI's own text leaves the sign/quiet/payload bit layout implementation-defined. Curry uses the standard IEEE-754 binary64 convention (essentially every real CPU's FPU agrees on this): bit 63 is the sign; bits 62–52 (`0x7ff`) mark the exponent field as NaN/infinity; of the 52-bit trailing significand, bit 51 (its own MSB) is the quiet/signaling flag (1 = quiet, 0 = signaling), and the low 51 bits are the payload.

## No single-precision support

Curry's numeric tower has no native single-precision float type — every flonum is a C `double`. `make-nan`'s optional `float` argument is validated (must be an inexact real, per the SRFI's own text) but never changes the constructed precision; every NaN this library produces or consumes is binary64. `nan=?`'s own spec text describes converting mismatched-precision arguments "to a precision at least as high as the higher-precision value" before comparing — with only one precision ever in play here, that step never actually does anything.

## Procedures

#### `(make-nan negative? quiet? payload [float])` → *NaN*

`payload` must be a positive exact integer no larger than `2^51 - 1` (raises otherwise — "positive exact integer" and "an error if payload is larger than a NaN can hold" are both the SRFI's own words). `float`, if given, must be an inexact real (validated, but ignored for precision selection — see above).

```scheme
(nan-payload (make-nan #f #t 42))   ; => 42
(nan-negative? (make-nan #t #t 1))  ; => #t
```

#### `(nan-negative? nan)` → *boolean*
#### `(nan-quiet? nan)` → *boolean*
#### `(nan-payload nan)` → *positive exact integer*

Each raises if `nan` isn't actually a NaN (checked via curry's own `nan?`).

#### `(nan=? nan1 nan2)` → *boolean*

`#t` if both NaNs have identical sign, quiet bit, and payload.

```scheme
(nan=? (make-nan #t #t 5) (make-nan #t #t 5))  ; => #t
(nan=? (make-nan #t #t 5) (make-nan #f #t 5))  ; => #f  -- sign differs
```

## A reader bug this library's own development surfaced

Writing this library's `nan-negative?`/`nan-quiet?`/`nan-payload` — each with a parameter literally named `nan` — hit a genuine, separate, pre-existing curry reader defect: the token `nan` alone (also `inf`, `infinity`, any case variant, no sign or decimal point) read back as a NaN/infinity **float**, not the symbol it should be. The cause: curry's numeric-literal fallback ultimately calls C's own `strtod`, and C99 mandates that `strtod` accept `"nan"`/`"inf"`/`"infinity"` (case-insensitively, `"nan"` even with an arbitrary parenthesized suffix) with no sign or decimal point required — none of which are valid R7RS numeric syntax (only the exact tokens `+nan.0`/`-nan.0`/`+inf.0`/`-inf.0` are, and those are matched separately, before this fallback is ever reached). Fixed in `src/reader.c`: a token must contain at least one digit before it's ever handed to `strtod` — every genuine float literal has one; none of `strtod`'s permissive-only spellings do.
