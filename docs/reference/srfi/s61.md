# SRFI-61 — `cond`'s extended arrow clause

No import needed — unlike every other library on the [availability table](index.md), SRFI-61 is not a `(srfi sN name)` shim. `cond` is one of curry's ~40 hardcoded special forms, dispatched directly by the compiler/evaluator on symbol identity rather than resolved through macro or environment lookup, so a library-level `define-syntax cond` shim is silently ignored (see [`s212.md`](s212.md) for the same wall hit from the other direction, aliasing). SRFI-61 could only ship by teaching the extended clause shape directly to both `compile_cond` (`src/compiler_classic.c`) and the tree-walker's `S_COND` case (`src/eval.c`) — always active, no `(import ...)` required.

[SRFI-61](https://srfi.schemers.org/srfi-61/): a more general `cond` clause, `(generator guard => receiver)`, alongside the three standard R7RS clause shapes.

#### `(cond ... (generator guard => receiver) ...)` — *syntax*

`generator` is evaluated once, via `call-with-values` semantics — it may return zero, one, or multiple values, unlike the standard `(test => proc)` clause, which only ever tests a single value's truthiness. `guard` is then applied to those same values; if the result is truthy, `receiver` is applied to the same values and its result becomes the whole `cond` expression's value. If `guard` returns `#f`, evaluation falls through to the next clause, exactly like a failed `test` in any other clause shape.

```scheme
(cond ((values 3 4) (lambda (a b) (< a b)) => (lambda (a b) (list 'less a b)))
      (else 'not-less))
; => (less 3 4)

;; A single-value generator still works -- it's wrapped as a one-element
;; argument list for guard/receiver:
(cond (5 (lambda (x) (> x 3)) => (lambda (x) (* x x))))
; => 25

;; Guard false falls through, same as any other clause:
(cond (5 (lambda (x) (> x 10)) => (lambda (x) 'never))
      (else 'fallthrough))
; => fallthrough
```

Distinguished from the standard 2-element arrow clause `(test => proc)` by shape: SRFI-61's clause body is three elements with `=>` as the *second* one (`guard => receiver`), vs. the standard clause's two elements with `=>` *first* (`=> proc`) — the two can never spuriously collide for any real clause.

The compiled path desugars to `call-with-values` + `apply` + a nested `cond` carrying the remaining clauses, exactly the machinery a hand-written expansion would use; the tree-walked path (used for `define-library` bodies) evaluates the generator once and unpacks a single/multi-value result into a shared argument list for `guard` and `receiver` directly.
