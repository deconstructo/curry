# `(srfi s279 inspect)` — SRFI-279

```scheme
(import (srfi s279 inspect))   ; or (srfi 279) / (srfi srfi-279)
```

[SRFI-279](https://srfi.schemers.org/srfi-279/) (*draft*, received 2026-08-11): a generic In(tro)spection Protocol for interactive REPLs/UIs — two procedures, `inspect-properties` and `inspect-describe`, that a rich object inspector can be built from without every implementation reinventing its own.

This is a **curry-native implementation**, not a port of the SRFI's own reference `generic.scm`: that file depends on SRFI 14 (char-sets), SRFI 26 (cut), SRFI 160 (numeric vectors), and SRFI 253 (checked lambdas), none of which curry has. Porting it would have meant building four other SRFIs first just to get this one working, so this module is written directly against curry's own primitives instead.

## `(inspect-properties object)` → *alist*

Returns a non-dotted alist (each entry `(key value)`, not `(key . value)`) of introspectable properties for `object`. Every object gets `write`/`display` entries (the object's own standard-procedure representations); the rest depends on `object`'s type. An unsupported property is *omitted*, never filled with a dummy `#f`.

```scheme
(inspect-properties 42)
; => ((write "42") (display "42") (real-part 42) (imag-part 0)
;     (numerator 42) (denominator 1) (real-sign 1) (real-base 2)
;     (integer->char #\*) (display-2 "101010") (display-8 "52") (display-16 "2a"))

(inspect-properties (list 1 2 3))
; => ((write "(1 2 3)") (display "(1 2 3)") (car 1) (cdr (2 3))
;     (last 3) (last-pair (3)) (length 3) (list->vector #(1 2 3))
;     (0 1) (1 2) (2 3))
```

### Supported types

| Type | Properties |
|------|------------|
| Every type | `write`, `display` |
| Number | `real-part`, `imag-part`; rationals additionally get `numerator`, `denominator`, `real-sign`, `real-base`; non-negative integers `≤ #x10FFFF` get `integer->char`; exact integers get `display-2`/`display-8`/`display-16` |
| Boolean | `boolean->integer` |
| Pair | `car`, `cdr`; proper non-circular lists (`list?`) additionally get `last`, `last-pair`, `length`, `list->vector`, indexed `0..N` elements, and `list->string` if every element is a character |
| Symbol | `symbol->string` |
| Character | `char->integer`, `char-alphabetic?`, `char-numeric?`, `char-whitespace?`, `char-upper-case?`, `char-lower-case?`; `digit-value` when the character is a digit |
| String | `string->symbol`, `string->list`, `string->vector`, `string->utf8`, `string-length`, indexed `0..N` characters; `string->number` when the string parses as one (never for the empty string — see [Known limitations](#known-limitations)) |
| Vector | `vector-length`, `vector->list`, indexed `0..N` elements; `vector->string` if every element is a character |
| Bytevector | `utf8->string`, indexed `0..N` byte values — see [Known limitations](#known-limitations) about `utf8->string`'s content for non-UTF-8 bytes |
| Error object (`error-object?`) | `error-object-message`, `error-object-irritants` |
| Hash table ([`(srfi 69)`](s69-s90.md)) | `hash-table-size`, every key inlined as `(key value)` |
| Box ([`(srfi 111)`](s111.md)) | `unbox` |
| Set ([`(srfi 113)`](s113.md)) | `set-size`, every element self-valued as `(element element)` |
| Bag ([`(srfi 113)`](s113.md)) | `bag-size`, `bag-unique-size`, every distinct element as `(element count)` — the SRFI's own suggested shape (a single `bag->set` delegating to set-properties) doesn't apply here since curry's `(srfi 113)` has no `bag->set` conversion; this reports counts directly instead, which is arguably more useful for something that's fundamentally a multiset |
| Record | `record-rtd`, every field inlined by name in field-definition order |
| Record type (RTD) | `rtd-name`, `rtd-field-names` |

`hash-table?`/`set?`/`bag?` are checked in that specific order: `(srfi 113)`'s bags are implemented as hash tables under the hood (`bag?` is literally `(and (hash-table? obj) ...)`), so `bag?` is checked *before* the generic `hash-table?` branch — otherwise every bag would get hash-table's property set instead of its own.

### Deliberately out of scope (not forgotten)

- **Procedure properties.** curry exposes no `procedure-name`/arity/arglist introspection to Scheme at all yet — a real gap, tracked separately from this SRFI, not something this module can paper over.
- **Numeric-vector (`s8vector` etc.) properties.** curry has no [SRFI 4](https://srfi.schemers.org/srfi-4/)/[SRFI 160](https://srfi.schemers.org/srfi-160/).
- **Char-set properties.** curry has no [SRFI 14](https://srfi.schemers.org/srfi-14/).
- **Library/environment properties.** `modules.c`'s registry has no Scheme-level enumeration API — module names/exports aren't queryable from Scheme once loaded.

## `(inspect-describe object [port])` → *unspecified*

Writes a human-readable description of `object` to `port` (default `(current-output-port)`). Currently just `write`s the object followed by a newline — the SRFI leaves "useful" up to the implementor, and curry's own REPL doesn't yet have a dedicated inspector UI for this to feed richer formatting into.

## New primitives this module is built on

`(srfi s279 inspect)`'s record-properties needed a way to ask "is this any record at all, and what type/fields does it have" without already knowing the record's RTD ahead of time — `define-record-type` only ever hands out a type-specific predicate/accessor set closed over one particular RTD. Four small primitives were added to close that gap, independently useful beyond this module:

- `(record? obj)` → *boolean* — `#t` iff `obj` is an instance of any record type.
- `(record-type? obj)` → *boolean* — `#t` iff `obj` is a record-type descriptor (RTD).
- `(record-rtd record)` → *RTD* — the RTD of `record`.
- `(record-type-name rtd)` → *symbol* — the type's name, as given to `define-record-type`.
- `(record-type-field-names rtd)` → *list of symbols* — field names, in field-definition order.

These match [`(rnrs records inspection)`](https://www.r6rs.org/final/html/r6rs-lib/r6rs-lib-Z-H-7.html#node_sec_7.3) naming (which curry's module system already aliases to the flat global env per the module-system docs, but had never actually implemented any procedures for until now).

## Known limitations

- **Circular objects hang, not gracefully.** curry's `write`/`display` have no cycle detection (no `#n=`/`#n#` datum labeling) — this is a pre-existing core gap, not something introduced by this module, but it means `(inspect-properties x)` will hang forever on any object containing a cycle, because `inspect-properties` always calls `write`/`display` on the object itself first (per the SRFI's own `object-properties` spec). Non-circular structure is unaffected: pair-properties' own list-walking uses `list?`, which *is* R7RS-mandated to detect cycles safely.
- **`(string->number "")` returns `0`, not `#f`, in this build** — a core numeric-parser bug independent of this module (R7RS requires `#f` for any string that isn't a valid number literal, and the empty string isn't one). `inspect-properties` explicitly guards the empty-string case so this bug doesn't leak a bogus `string->number` entry into every empty string's properties, but the underlying bug itself is unfixed. (Every other edge case tested — whitespace-only strings, bare `.`/`+`/`-` — already correctly returns `#f`, so this guard covers the actual scope of the bug.)
- **`utf8->string` never validates its input** — curry's `utf8->string` does a raw byte copy with no UTF-8 validation (it cannot raise on malformed input, unlike some R7RS implementations). `bytevector-properties`' `utf8->string` entry is therefore always present, but for a bytevector that isn't valid UTF-8 its content is garbled rather than a real decode — there's no reliable way for this module to detect that case and omit the entry instead.
