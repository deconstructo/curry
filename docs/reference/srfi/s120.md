# `(srfi s120 timer)` — SRFI-120

```scheme
(import (srfi s120 timer))   ; or (srfi 120), or (srfi srfi-120)
```

[SRFI-120](https://srfi.schemers.org/srfi-120/) Timer APIs: schedule a thunk to run once or repeatedly, after a delay, without hand-rolling a sleep loop. Each timer owns one dedicated background thread (spawned via curry's actor system) that sleeps on a real, interruptible timed condition-variable wait (`(curry sync)`'s `cond-wait-timeout!`) until either the next task's deadline arrives or a scheduling call wakes it early — not a polling loop.

All deadline arithmetic is done against `current-jiffy` (`CLOCK_MONOTONIC`-backed — see `src/builtins.c`), not wall-clock time, so a system clock adjustment during a program's run can't make a task fire early/late or a periodic task's cadence drift.

## Timers

#### `(make-timer)` → *timer*
#### `(make-timer error-handler)` → *timer*

Creates and starts a timer immediately (there's no separate "start" step). `error-handler`, if given, is a 1-argument procedure invoked with the condition whenever a scheduled task's thunk raises an uncaught error; the timer keeps running afterward. **Without an `error-handler`, an uncaught error in any task's thunk stops the timer** (as if `timer-cancel!` had been called) and preserves the condition for `timer-cancel!` to re-raise — see below.

#### `(timer? obj)` → *boolean*

#### `(timer-cancel! timer)`

Stops `timer` permanently — its background thread exits and no further tasks (however already scheduled) will run. A timer cannot be restarted once cancelled. If the timer was stopped by an unhandled task error (rather than an explicit `timer-cancel!` call), this call re-raises that condition; the condition is delivered at most once, so a second `timer-cancel!` on an already-stopped timer is a harmless no-op.

```scheme
(define t (make-timer))
(timer-schedule! t (lambda () (error "boom")) 10)
(timer-cancel! t)  ; => raises the "boom" condition, ~10ms later
```

## Scheduling

#### `(timer-schedule! timer thunk when)` → *task-id*
#### `(timer-schedule! timer thunk when period)` → *task-id*

Schedules `thunk` to run once, `when` in the future. `when` is either a non-negative exact integer (milliseconds) or a [timer-delta](#timer-deltas) object. If `period` is given (same shape as `when`), the task is periodic: after each run, its next occurrence is scheduled `period` after the occurrence that just ran (`when` + `period`, a single addition — not a catch-up loop that fires repeatedly to make up for lost time if the timer fell behind). Returns a task id (an exact integer, unique among `timer`'s own currently-scheduled tasks) usable with `timer-reschedule!`/`timer-task-remove!`/`timer-task-exists?`.

A periodic task's own id remains valid and refers to its *next* occurrence for the entire time its current occurrence's thunk is running — the currently-executing occurrence always runs to completion regardless of what happens to the id in the meantime (including the thunk rescheduling or removing itself). Raises if `timer` has already been cancelled (explicitly, or by an unhandled error).

```scheme
(define t (make-timer))
(timer-schedule! t (lambda () (display "tick\n")) 1000 1000)  ; every second, starting in 1s
(timer-schedule! t (lambda () (display "once\n")) (make-timer-delta 500 'ms))
```

#### `(timer-reschedule! timer id when)` → *id*
#### `(timer-reschedule! timer id when period)` → *id*

Changes task `id`'s next deadline to `when` from now. If `period` is given, it replaces the task's period; **`period` of `0` cancels the periodic aspect**, making the task one-shot from here on. Raises if `id` isn't currently associated with `timer` — which includes a one-shot task that has already executed and been removed (there's no separate "already executed" bookkeeping: a used-up one-shot id and a never-issued id are indistinguishable, both simply "not found").

#### `(timer-task-remove! timer id)` → *boolean*

Removes task `id` before it next runs. Returns `#t` if a task was actually removed, `#f` if `id` wasn't found (including a one-shot task that already ran). Safe to call from within a task's own thunk (including on its own id, for a periodic task — see above).

#### `(timer-task-exists? timer id)` → *boolean*

`#t` if `id` currently refers to a pending (not-yet-executed, not-removed) task on `timer`.

## Timer deltas

#### `(make-timer-delta n unit)` → *timer-delta*

A duration of `n` `unit`s, for use as `timer-schedule!`/`timer-reschedule!`'s `when`/`period` arguments as an alternative to a plain millisecond integer. `unit` is one of the symbols `h` `m` `s` `ms` `us` `ns` (hours/minutes/seconds/milliseconds/microseconds/nanoseconds — the full required set from the SRFI; curry defines no additional units). Raises on an unrecognized unit.

#### `(timer-delta? obj)` → *boolean*

```scheme
(timer-schedule! t thunk (make-timer-delta 2 'h))       ; in 2 hours
(timer-schedule! t thunk 0 (make-timer-delta 30 's))    ; now, then every 30s
```

## Implementation notes

- **Dynamic environment.** The SRFI says "tasks execute in the dynamic environment where timer was created." This implementation makes no special effort to capture/replay `parameterize`/`dynamic-wind` state from the creating thread into the scheduler thread — it runs each task's thunk directly on the timer's own dedicated background thread, which (like any freshly spawned curry actor) starts with a fresh dynamic extent of its own. This matches the SRFI's own reference implementation, which is similarly just riding on top of whatever the host Scheme's own SRFI-18 threads give it "for free," with no explicit capture/replay machinery either.
- **Task ids** are plain incrementing exact integers, one counter per timer — unique per timer, not globally, which is all the SRFI itself requires ("a readable datum, typically an integer").
- **"Self-rescheduled tasks continue current execution then reschedule" vs. "tasks can cancel/reschedule other tasks but not themselves."** These two pieces of the SRFI's own text read as somewhat in tension for periodic tasks. This implementation resolves it by reinserting a periodic task's next occurrence into the schedule *before* running the current occurrence's thunk (not after) — so the id is always valid and any reschedule/removal against it (whether from that task's own thunk or another task's) affects the *upcoming* occurrence, never the one currently running to completion.
- **Error handling** without a configured `error-handler` doesn't introduce a separate "halted-by-error" state distinct from an explicit `timer-cancel!` — from the outside they're the same: the timer's background thread has exited, and any preserved condition is delivered by the next `timer-cancel!` call. Every mutating operation (`timer-schedule!`/`timer-reschedule!`/`timer-task-remove!`) already needs to treat "already stopped" as an error case regardless of *why* it stopped, so a single `cancelled?` flag covers both origins without added complexity.
