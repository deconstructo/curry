# `(srfi s64 testing)` — SRFI-64

```scheme
(import (srfi s64 testing))
```

[SRFI-64](https://srfi.schemers.org/srfi-64/): a full unit-testing framework — test cases, named test groups, skip/expect-fail specifiers, pluggable test runners, and machine-readable per-test result properties. Curry's own `tests/*.scm` R7RS/R6RS conformance suites are written against this library. [`(srfi s252 property-testing)`](s252.md) builds property-based testing on top of it.

## Test cases

Each of these takes an optional leading `name` string; the report uses it (or the source expression, if unnamed) to identify a failure.

#### `(test-assert [name] expr)`

Passes if `expr` is truthy.

#### `(test-equal [name] expected expr)`
#### `(test-eqv [name] expected expr)`
#### `(test-eq [name] expected expr)`

Passes if `expr` is `equal?`/`eqv?`/`eq?` to `expected`.

#### `(test-approximate [name] expected expr error)`

Passes if `(<= (abs (- expr expected)) error)`.

#### `(test-error [name-or-type] [type] expr)`

Passes if `expr` raises. With no type argument, any raised condition passes. With a `type` argument (a one-argument predicate, e.g. `error-object?` — curry has no SRFI-36 condition-type hierarchy to match against by name), only a condition satisfying `(type condition)` passes.

```scheme
(test-begin "arithmetic")
(test-assert "positive" (> 5 0))
(test-equal "sum" 4 (+ 2 2))
(test-approximate "pi" 3.14159 (* 4 (atan 1)) 0.001)
(test-error "car-of-empty" (car '()))
(test-end "arithmetic")
```

Any uncaught exception raised by `expr` inside `test-assert`/`test-equal`/`test-eqv`/`test-eq`/`test-approximate` is caught and counted as a failure, not propagated — a bug in the code under test doesn't abort the rest of the suite.

#### `(test-read-eval-string str)`

Reads exactly one datum from `str`, evaluates it in the interaction environment, and returns the result; raises if `str` contains anything besides that one datum.

## Test groups

#### `(test-begin suite-name [count])`
#### `(test-end [suite-name])`

Brackets a named group of test cases. If the first `test-begin` in a program has no enclosing runner already installed, one is created automatically (via `test-runner-factory`) and torn down at the matching outermost `test-end`. The optional `count` on `test-begin` is checked against the actual number of test cases run in the group at `test-end` (invoking `test-runner-on-bad-count` if they don't match); the optional name on `test-end` is checked against `test-begin`'s (invoking `test-runner-on-bad-end-name` if they don't match).

#### `(test-group suite-name decl ...)`
#### `(test-group-with-cleanup suite-name decl ... cleanup)`

`test-begin`/`decl ...`/`test-end`, wrapped in `dynamic-wind` so `test-end` (and `cleanup`, for the `-with-cleanup` form) still runs if `decl ...` raises or escapes.

```scheme
(test-group "nested"
  (test-assert (> 2 1))
  (test-group "deeper" (test-assert #t)))
```

## Skip and expect-fail specifiers

#### `(test-skip specifier)`
#### `(test-expect-fail specifier)`

Registers `specifier` (a string, matched exactly against a test's name, or a one-argument predicate on the name) against the current group: matching test cases are recorded as `skip` (never run) or have their outcome flipped to `xpass`/`xfail` (run normally, but a pass/fail doesn't count as a suite failure) respectively. Cleared automatically at the matching `test-end`.

#### `(test-match-name name)`
#### `(test-match-nth n [count])`
#### `(test-match-any spec ...)`
#### `(test-match-all spec ...)`

Specifier constructors: exact name match, the `n`-th (through `n + count - 1`-th) test case encountered, or a combination of other specifiers.

## Test runners

A test runner is an opaque record accumulating pass/fail/xpass/xfail/skip counts and dispatching to callback hooks at each lifecycle point.

#### `(test-runner-null)` → *runner, all callbacks no-ops*
#### `(test-runner-simple)` → *runner, prints failures as they happen and a summary (with `(exit 1)` on any failure) at `test-end`*
#### `(test-runner-create)` → *`((test-runner-factory))`*
#### `(test-runner-factory)` → *parameter, defaults to `test-runner-simple`*
#### `(test-runner-current)` → *parameter, the active runner (or `#f`)*
#### `(test-runner-get)` → *the active runner, or raises if none*
#### `(test-with-runner runner decl ...)` — *syntax*, `(parameterize ((test-runner-current runner)) decl ...)`
#### `(test-apply arg ...)`

`(test-apply [runner] specifier ... thunk)`: installs `runner` (or the current one) with every test *not* matching any `specifier` skipped, then calls `thunk`.

```scheme
(test-with-runner (test-runner-simple)
  (test-begin "suite")
  (test-assert (= 1 1))
  (test-end "suite"))
```

### Runner accessors

`test-runner-pass-count`, `test-runner-fail-count`, `test-runner-xpass-count`, `test-runner-xfail-count`, `test-runner-skip-count`, `test-runner-test-name`, `test-runner-group-path`/`test-runner-group-stack`, `test-runner-aux-value`/`test-runner-aux-value!` (a free slot for a custom runner's own state), `test-runner-reset`. Only the getters are exported for the count fields — there's no public `test-runner-pass-count!` and friends, since counting is entirely `%do-case`'s (private) responsibility; a library wanting to record its own outcomes in that same bookkeeping should route through `%run-assert` (see [`s252.md`](s252.md) for a worked example of exactly that).

### Callback hooks

Each has a getter and a `!` setter: `test-runner-on-test-begin`, `test-runner-on-test-end`, `test-runner-on-group-begin`, `test-runner-on-group-end`, `test-runner-on-bad-count`, `test-runner-on-bad-end-name`, `test-runner-on-final`. `test-runner-simple`'s own callback implementations are also exported individually as `test-on-test-begin-simple`, `test-on-test-end-simple`, `test-on-group-begin-simple`, `test-on-group-end-simple`, `test-on-bad-count-simple`, `test-on-bad-end-name-simple`, `test-on-final-simple` — useful for building a custom runner that reuses most of `test-runner-simple`'s behavior but overrides one hook (`property-test-runner` in [`s252.md`](s252.md) does exactly this).

## Result properties

After each test case, its outcome is available as a small alist on the runner:

#### `(test-result-kind [runner])` → *one of `'pass` `'fail` `'xpass` `'xfail` `'skip`, or `#f`*
#### `(test-passed? [runner])` → *`#t` iff the kind was `'pass` or `'xpass`*
#### `(test-result-ref runner property [default])`
#### `(test-result-set! runner property value)`
#### `(test-result-remove runner property)`
#### `(test-result-clear runner)`
#### `(test-result-alist runner)`

Standard properties set by the built-in test cases include `'result-kind`, `'test-name`, `'source-form`, `'actual-value`, and `'actual-error` (when the case raised). `test-result-set!` is additive — a custom test form can attach its own properties onto a result that `%run-assert` already populated, without disturbing the standard ones.
